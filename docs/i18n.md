# Localization and i18n

Contfu represents localized content as flat item variants: one item per locale. Localized items expose a normalized `$locale` property, and applications choose which locale to query.

## Responsibilities

Contfu separates localization setup from application locale preferences:

- The **Cloud Service** defines how content is localized: active locales, locale mapping, locale fields, and fallback grouping keys.
- The **Local Runtime** stores localized item variants in the Local Store and applies locale/fallback query behavior.
- The **Application** chooses its default locale and fallback locale through the query client or server configuration.

This keeps provider-specific setup out of application code while still letting each application decide what locale it wants to render.

## Localized collections

A localized collection contains item variants associated with locales. Each delivered localized item has `$locale` set to a normalized BCP 47 locale tag, for example `en`, `en-US`, or `de`.

Provider integrations may detect localization automatically. For providers or collections that do not expose localization metadata, you can define a localization layer manually by choosing active locales and a locale field.

### Active locales

Active locales are the locales selected for synchronization and generated application types.

If a provider detects more locales than you want to use, you can restrict the active locale list. Inactive detected locales are ignored: they are not synchronized, counted, warned about, or delivered to applications.

Changing active locales changes the application contract. Regenerate types after changing active locales.

### Locale resolution and mapping

Active locales are canonical application contract values such as `en`, `en-US`, and `de`. Raw source values are resolved in this order:

1. Explicit locale map override.
2. Automatic detection.

Automatic detection recognizes common BCP 47 casing and separator variants such as `en`, `EN`, `en-US`, and `en_US`, plus curated English and native language names such as `English`, `German`, and `Deutsch` when they point to an active locale.

Locale maps are for deliberate overrides or source-specific labels Contfu cannot infer. For example, map `en-US` to `en` when the source uses regional English but your application contract only exposes base English:

| Raw value           | Locale |
| ------------------- | ------ |
| `en-US`             | `en`   |
| `Editorial English` | `en`   |

A mapping that duplicates automatic detection, such as `English` → `en` or `Deutsch` → `de`, is optional. The UI shows a non-blocking hint for these redundant mappings instead of treating them as errors.

Locale map keys are raw source strings. Locale map values must resolve to active locales.

### Raw locale field

Contfu normally removes the raw locale field after it has produced `$locale`. You can keep it when you need the original provider value for diagnostics or application filtering, but `$locale` should be the canonical field used by application code.

## Fallback grouping key

Fallback needs to know which localized items are translations of the same logical content item. The **Fallback grouping key** is the collection property shared by those translations.

For example, if these two items are translations of the same article:

| slug       | title    | $locale |
| ---------- | -------- | ------- |
| `about-us` | About us | `en`    |
| `about-us` | Über uns | `de`    |

then `slug` can be the fallback grouping key.

The fallback grouping key:

- is used only when fallback is enabled;
- does not change item identity;
- does not need to be globally unique across collections;
- should be unique enough within a collection to avoid pairing unrelated items;
- must be a stable scalar property shared by translated variants.

If a localized collection has no fallback grouping key, locale filtering still works, but fallback queries cannot be applied for that collection.

## Querying localized content

### Embedded local runtime

Use `@contfu/contfu` when your application runs next to the Local Store:

```ts
import { contfu } from "@contfu/contfu";

const { query } = contfu({
  i18n: {
    defaultLocale: "de",
    fallback: "en",
  },
});

const posts = await query("blogPost");
```

### HTTP client

Use `@contfu/client` when your application queries a Contfu Server over HTTP:

```ts
import { contfuClient } from "@contfu/client";

const query = contfuClient("https://content.example.com", "token", {
  i18n: {
    defaultLocale: "de",
    fallback: "en",
  },
});

const posts = await query("blogPost");
```

### Server defaults

A Contfu Server can provide defaults for HTTP clients that do not send locale preferences:

```ts
import serve from "@contfu/server";

serve({
  i18n: {
    defaultLocale: "de",
    fallback: "en",
  },
});
```

The packaged server image also supports environment defaults:

```sh
CONTFU_DEFAULT_LOCALE=de
CONTFU_FALLBACK_LOCALE=en
```

`CONTFU_FALLBACK_LOCALE=true` means “fall back to `CONTFU_DEFAULT_LOCALE`”. `CONTFU_FALLBACK_LOCALE=false` disables fallback as the server default.

## Per-query overrides

Query options override client and server defaults:

```ts
// Request a specific locale
await query("blogPost", { locale: "en" });

// Request a specific locale with a specific fallback
await query("blogPost", { locale: "fr", fallback: "en" });

// Fall back to the configured default locale
await query("blogPost", { locale: "fr", fallback: true });

// Disable fallback for this query
await query("blogPost", { locale: "fr", fallback: false });

// Return all locales and suppress default locale selection
await query("blogPost", { locale: false });
```

You can also create a scoped query client for request-local rendering:

```ts
const localizedQuery = query.withLocale(requestLocale, "en");
const posts = await localizedQuery("blogPost");
```

## Explicit `$locale` filters

If your query filter explicitly references `$locale`, Contfu does not add implicit locale or fallback behavior:

```ts
await query("blogPost", {
  filter: (p) => query.eq(p.$locale, "en"),
});
```

Use this when you want full control over locale filtering.

## Generated types

Generated application types include:

- a global `Locale` union containing active locales;
- `$locale: Locale` on localized collections.

Regenerate types after changing active locales or localization metadata.

## Invalid locale values

For localized collections, every delivered item must resolve to an active locale after locale map overrides and automatic detection have run. Missing, invalid, unmapped, or unexpected locale values are held and reported as aggregated validation incidents instead of being delivered with an invalid `$locale`.

For example, `English` is delivered as `en` when `en` is active, while an unknown label such as `Editorial English` is held until you add an explicit locale map entry. `en-US` is held when only `en` is active unless you deliberately map `en-US` to `en`.

Inactive detected locales are different: they are intentionally ignored and do not create incidents.
