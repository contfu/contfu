# Localization and i18n

Contfu represents localized content as flat item variants: one item per locale. Localized items expose a normalized `$locale` property, and applications choose which locale to query.

## Responsibilities

Contfu separates localization setup from application locale preferences:

- The **Contfu** defines how content is localized: active locales, locale mapping, locale fields, and fallback grouping keys.
- The **Contfu runtime** stores localized item variants in the Local Store and applies locale/fallback query behavior.
- The **Application** chooses its default locale and fallback locale through the query client or server configuration.

This keeps service-specific setup out of application code while still letting each application decide what locale it wants to render.

## Localized collections

A localized collection contains item variants associated with locales. Each delivered localized item has `$locale` set to a normalized BCP 47 locale tag, for example `en`, `en-US`, or `de`.

Service Integrations may detect localization automatically. For Services or collections that do not expose localization metadata, you can define a localization layer manually by choosing active locales and a locale field.

### Active locales

Active locales are the locales selected for synchronization and generated application types.

If a Service detects more locales than you want to use, you can restrict the active locale list. Inactive detected locales are ignored: they are not synchronized, counted, warned about, or delivered to applications.

Changing active locales changes the application contract. Regenerate types after changing active locales.

### Locale resolution and mapping

Active locales are canonical application contract values such as `en`, `en-US`, and `de`. Raw source values are resolved in this order:

1. Explicit locale map override.
2. Automatic detection.

Automatic detection recognizes common BCP 47 casing and separator variants such as `en`, `EN`, `en-US`, and `en_US`, plus curated English and native language names such as `English`, `German`, and `Deutsch` when they point to an active locale.

Locale maps are for deliberate overrides or source-specific labels Contfu cannot infer. For example, map `en-US` to `en` when the source uses regional English but your application contract only exposes base English:

| Raw value           | Locale |
| ------------------- | ------ |
| `en-US`             | `en`   |
| `Editorial English` | `en`   |

A mapping that duplicates automatic detection, such as `English` → `en` or `Deutsch` → `de`, is optional. The UI shows a non-blocking hint for these redundant mappings instead of treating them as errors.

Locale map keys are raw source strings. Locale map values must resolve to active locales.

### Raw locale field

Contfu normally removes the raw locale field after it has produced `$locale`. You can keep it when you need the original Service value for diagnostics or application filtering, but `$locale` should be the canonical field used by application code.

### Strapi relation refs

For localized Strapi content, item refs use Strapi's raw entry locale, for example `article001:de`. Relation props follow the related entry payload returned by Strapi: when a relation object includes a non-empty `locale`, Contfu encodes the relation ref with that same locale, such as `author001:de`; when Strapi omits the relation locale, the relation remains document-level, such as `author001`.

This is independent of whether Contfu fetched `locale=all` or a selected Strapi locale scope. Locale mapping still applies later when producing `$locale`; relation refs match the raw Service item refs used for registry resolution.

## Fallback grouping key

Fallback needs to know which localized items are translations of the same logical content item. The **Fallback grouping key** is the collection property shared by those translations.

For example, if these two items are translations of the same article:

| slug       | title    | $locale |
| ---------- | -------- | ------- |
| `about-us` | About us | `en`    |
| `about-us` | Über uns | `de`    |

then `slug` can be the fallback grouping key.

The fallback grouping key:

- is used only when fallback is enabled;
- does not change item identity;
- does not need to be globally unique across collections;
- should be unique enough within a collection to avoid pairing unrelated items;
- must be a stable scalar property shared by translated variants;
- must be a normal collection property, not a system field such as `$locale`, `$ref`, or `$draft`.

If a localized collection has no fallback grouping key, locale filtering still works, but fallback queries cannot be applied for that collection.

## Querying localized content

### Embedded runtime

Use `@contfu/contfu` when your application runs next to the Local Store:

```ts
import { contfu } from "@contfu/contfu";

const { query } = contfu({
  i18n: {
    defaultLocale: "de",
    fallback: "en",
  },
});

const posts = await query("blogPost");
```

### HTTP client

Use `@contfu/client` when your application queries a Contfu Server over HTTP:

```ts
import { contfuClient } from "@contfu/client";

const query = contfuClient("https://content.example.com", "token", {
  i18n: {
    defaultLocale: "de",
    fallback: "en",
  },
});

const posts = await query("blogPost");
```

### Server defaults

A Contfu Server can provide defaults for HTTP clients that do not send locale preferences:

```ts
import serve from "@contfu/server";

serve({
  i18n: {
    defaultLocale: "de",
    fallback: "en",
  },
});
```

The packaged server image also supports environment defaults:

```sh
CONTFU_DEFAULT_LOCALE=de
CONTFU_FALLBACK_LOCALE=en
```

`CONTFU_FALLBACK_LOCALE=true` means “fall back to `CONTFU_DEFAULT_LOCALE`”. If no default locale is configured, an inherited `true` fallback is ignored. `CONTFU_FALLBACK_LOCALE=false` disables fallback as the server default.

## Per-query overrides

Query options override client and server defaults:

```ts
// Request a specific locale
await query("blogPost", { locale: "en" });

// Request a specific locale with a specific fallback
await query("blogPost", { locale: "fr", fallback: "en" });

// Fall back to the configured default locale
await query("blogPost", { locale: "fr", fallback: true });

// Disable fallback for this query
await query("blogPost", { locale: "fr", fallback: false });

// Return all locales and suppress default locale selection
await query("blogPost", { locale: false });
```

Per-query `fallback: true` requires a configured default locale so Contfu knows which locale to fall back to.
Inherited fallback defaults that cannot resolve to a default locale are ignored instead of failing queries.

You can also pass the same HTTP query overrides through the CLI query helpers:

```bash
contfu items query -u <server-url> --collection blogPost --locale fr --fallback en
contfu items count -u <server-url> --collection blogPost --locale false --fallback false
```

Or create a scoped query client for request-local rendering:

```ts
const localizedQuery = query.withLocale(requestLocale, "en");
const posts = await localizedQuery("blogPost");
```

## Explicit `$locale` filters

If your query filter explicitly references `$locale`, Contfu does not add implicit locale or fallback behavior:

```ts
await query("blogPost", {
  filter: (p) => query.eq(p.$locale, "en"),
});
```

Use this when you want full control over locale filtering.

## Generated types

Generated application types include:

- a global `Locale` union containing active locales;
- `$locale: Locale` on localized collections.

Regenerate types after changing active locales or localization metadata.

## Invalid locale values

For localized collections, every delivered item must resolve to an active locale after locale map overrides and automatic detection have run. Missing, invalid, unmapped, or unexpected locale values are held and reported as aggregated validation incidents instead of being delivered with an invalid `$locale`.

For example, `English` is delivered as `en` when `en` is active, while an unknown label such as `Editorial English` is held until you add an explicit locale map entry. `en-US` is held when only `en` is active unless you deliberately map `en-US` to `en`.

Inactive detected locales are different: they are intentionally ignored and do not create incidents.

### Localized Strapi targets (v5 only)

Localized delivery requires an explicitly selected **Strapi API version: v5**, the
updated Contfu Strapi plugin on the receiver, and a discovered localized collection
with a configured **grouping key**. Missing API-version configuration and v4 remain
`not-localized`; they do not silently discard `$locale` from localized deliveries.
Unlocalized targets retain their existing delivery behavior. Localized single types are
not supported; this contract covers Strapi collection types.

Map `$locale` unchanged, exactly once, and map a stable string or number grouping
key unchanged to the target field. Every locale variant of one document must use
the same key; unrelated documents must use different keys. Defaults, array extraction,
casts, and locale remapping are intentionally unsupported for localized Strapi targets
in this release. Configure matching locale codes on both services. Incompatible flows
are frozen with an I18N contract diagnostic, not a credential failure.

Contfu resolves the grouping key across all authored remote locales and draft/published
states. More than one document is an error; zero documents is also an error when an
existing binding or sibling variant requires one. Only the first variant without an
expected sibling may create a document. Updates never recreate a missing bound document.
Binding recreation/full resync resolves the same document and fails closed on ambiguity.
Only authored values are delivered; fallback-resolved translations are not materialized.

Each target binding is an opaque, versioned `(documentId, locale)` identity. Per-locale
updates and deletes include the native locale explicitly. `$draft: true` writes the draft
and uses the plugin's authenticated Document Service unpublish operation for that locale;
publishing uses `status=published`. Neither operation unpublishes or deletes sibling locales.
Changing a bound locale or grouping identity is rejected rather than silently moving data.

Legacy raw target bindings are retained and quarantined as permanent failed deliveries.
An organization owner/admin who is also a member of the active workspace can use
**Integrations → webhook diagnostics → outbound failed deliveries → repair localized binding**.
Confirming resolves the current item's locale/key to exactly one remote document,
replaces only that binding, and queues redelivery. Ordinary redelivery does not repair it.
If the source is unavailable/deleted, the plugin is unavailable, or lookup is ambiguous,
repair leaves the binding unchanged. Restore source evidence or resolve the remote ambiguity
before retrying; do not guess a document ID.

Repair attempts are durably workspace-audited: actor, collection/item, failed revision,
SHA-256 digest of the old binding (never its raw value), new composite identity, outcome,
and timestamp. Remote credentials and payloads are excluded. Cross-workspace failures
are non-enumerating. The authenticated API action is
`POST /api/v1/target-deliveries/failed/:id` with `{"action":"repair-strapi-binding"}`;
the same owner/admin and workspace checks apply to API keys.

Localized Strapi relation bindings use the matching delivery locale. Cross-locale relation
bindings are rejected: Strapi resolves localized REST relations in the document's locale,
so accepting a different binding locale could silently connect a different translation.

#### Localized target recovery and operational limits

Localized target bindings retain an indexed grouping identity (field name and typed value)
independently of source caches. Only bindings in that group participate in sibling checks.
Expired file URLs, missing source memberships, or disabled paths on unrelated items do not
block delivery. A verified same-group binding remains usable without its source cache;
a missing remote document or conflicting sibling identity still fails closed. Old bindings
acquire this metadata on delivery or repair; remote grouping lookup remains authoritative.

Quarantined legacy bindings create item-level failed deliveries, not collection suspensions.
For a failed **deletion**, do not clear the failure or reset the target binding: that would
lose the link to the remote locale. Restore the original source evidence (same managed item,
grouping key, and locale) and enabled flow path, then use owner/admin binding repair. Repair
queues the original deletion, not an upsert, and only that locale is deleted. If the evidence
cannot be restored, retain the failure until an operator has independently verified and
removed the intended remote locale; never infer a document ID from a legacy raw binding.

Localized writes currently serialize per target collection and hold a transaction across
remote schema lookup, uploads, and writes. Indexed sibling lookup removes collection-size
source-resolution work, but remote latency still limits collection throughput and long
uploads can exhaust transaction/connection timeouts. Monitor delivery duration and backlog;
this is not a parallel-write path. Do not reduce lock coverage without preserving first-variant
creation and repair serialization. Apply the migration and restart the backend after deployment.

The disposable Strapi fixture validates native authentication, routing, publication, and
locale deletion; backend worker/repair specs separately validate obligation orchestration.
It does not constitute an end-to-end backend full-resync test against a real Strapi instance.
